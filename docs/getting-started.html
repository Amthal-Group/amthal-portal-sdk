Integration guide

Getting started

This page takes you from an empty project to a real Amthal form rendering inside your app. It is written to be followable end to end without asking anyone a question — every value you need is either something Amthal hands you once, or something you can read off the API yourself with a curl command printed below.

Budget about half an hour on a project that already builds. Roughly two thirds of that is getting registry access and your first token; the SDK integration itself is one component and three callbacks.

What you are building

The Amthal Portal SDK embeds the Amthal Client Portal — including its form builder — inside your own mobile app. Your app owns the login, the navigation and the screen around it; the SDK owns a hardened WebView pointed at the portal's /embed/* routes, and a small message bridge that carries credentials, locale, theme and lifecycle events between the two. The user never sees a browser, never logs in twice, and the form they fill is the same form the portal serves on the web, themed for your tenant.

Four packages exist, one per host runtime. They are interchangeable in behaviour, not in code shape — pick the one that matches your app and ignore the rest.

React Native (inline)

@amthal-group/portal-react-native

A pure-TypeScript component over react-native-webview. Renders inline, so you can put it inside your own screen, tab or modal. This is the only host that supports form delegation.

Expo (native sheet, iOS only)

@amthal-group/portal-expo

Presents the native iOS SDK in a UISheetPresentationController from JavaScript. Its module declares Apple as its only platform — on Android, use the React Native wrapper.

iOS (Swift)

SwiftPM library AmthalPortal

A UIViewController plus a SwiftUI wrapper. iOS 15 and up. Added by Git URL or as a local package.

Android (Kotlin)

com.amthalgroup:portal-sdk

An Activity, a Fragment and a bare FrameLayout view. minSdk 24, compileSdk 35, JVM target 17.

All four speak the same wire protocol — Amthal Bridge Protocol v1 — and all four ship as version 1.0.0. The protocol version is compared for strict equality against the portal's manifest, so an SDK and a portal either agree or the SDK refuses to load; there is no partial-compatibility mode.

1. Your app authenticates Your own login screen, against the Optimum Core API. You keep the token.
2. You open the SDK Hand it baseUrl, the token, the branchId and which form to show.
3. The SDK checks the portal Fetches /embed/manifest.json and compares protocol and version floors before showing anything.
4. The bridge handshakes The portal sends hello, the SDK replies init with your credentials and locale/theme.
5. The form renders The portal sends ready, the SDK hides its splash, and your user is on the form.
6. Submission comes back to you onSubmitted fires with the application number. The SDK never auto-closes — what happens next is your decision.

1 — Prerequisites: Amthal's side and yours

Five values have to exist before any code can work. Three of them only Amthal can give you; two you can read off the API once you have the first three. Collect all five before you start — every one of them has a failure mode that looks like a bug in the SDK.

What Amthal provisions for you

ValueWhat it isHow to confirm it is right
Portal base URL The deployed Client Portal, including its deploy path prefix. The portal ships with <base href="/portal/">, so a typical value is https://portal.example.com/portal. curl -s {baseUrl}/embed/manifest.json returns JSON, not HTML.
API base URL The Optimum Core API host that the portal itself talks to. Your login and token-refresh calls go here. It is not the same host as the portal. POST {api}/Portal/Authentication/Authenticate answers.
A test customer login A real customer/contact account on the branch you are integrating. It returns a token from Authenticate.

What you work out yourself

ValueWhat it isWhere it comes from
branchId The tenant/organisation whose forms, workflow and branding apply. A numeric id, passed as a string. Step 5 — one anonymous GET.
productID The id of the specific form in the DMS catalogue. Step 7 — one catalogue GET.

You also need a GitHub personal access token to install the packages (step 2). That one is yours to create, not Amthal's to issue.

The SDK never shows a login screen. It has no account UI, no password field and no session of its own. Authentication stays entirely in your app: you obtain a token however you already do, and hand it over the bridge. This is deliberate — credentials never travel in a URL, and your app keeps one identity rather than two.

2 — Access the package registry

The @amthal-group/* npm packages and the Android artifact are published to GitHub Packages, which requires authentication even for reads. Create a GitHub personal access token (classic) with the read:packages scope — no other scope is needed, and a token with more scope than that is a liability in a build machine's home directory.

npm — React Native and Expo

Put these two lines in your user-wide ~/.npmrc, never in the repository:

@amthal-group:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=ghp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

Verify before going further:

npm view @amthal-group/portal-react-native version
# → 1.0.0

A 401 Unauthorized here means the token is missing, expired, or lacks read:packages — nothing after this step will work until that command prints a version. In CI, inject the token as a secret and write the same two lines at build time.

Gradle — native Android

The same token, supplied to Gradle as gpr.user / gpr.key in ~/.gradle/gradle.properties. Never commit them.

Working from a checkout of the SDK monorepo instead? You need no token at all. npm install at the repository root resolves the wrappers through npm workspaces; run npm run build once to build the bridge package, then depend on the wrapper by path. npm run typecheck type-checks all three JS workspaces.

3 — Install for your platform

React Native Expo iOS Android

React Native (inline)

npm install @amthal-group/portal-react-native react-native-webview
cd ios && pod install

Peer dependencies: react ≥ 18, react-native ≥ 0.72, react-native-webview ≥ 13. The wrapper itself is pure TypeScript and contains no native code — the pod install is for the WebView.

Expo (native iOS sheet)

npm install @amthal-group/portal-expo
npx expo prebuild
npx expo run:ios

Peers: expo, expo-modules-core, react ≥ 18, react-native ≥ 0.72. The pod targets iOS 15.1 and Swift 5.9.

Expo Go cannot run either wrapper. Both paths involve native code — the WebView in one, an Expo module with a Swift pod in the other — so you need a development build. And note that the Expo module declares "platforms": ["apple"]: there is no Android sheet. An Expo app that must work on both platforms uses @amthal-group/portal-react-native for Android.

iOS (Swift Package Manager)

A Package.swift at the repository root declares the library AmthalPortal, so SwiftPM resolves the SDK straight from the Git URL. In Xcode: File ▸ Add Package Dependencies… and paste the repository URL. Or, in your own manifest: 

dependencies: [
    // No release has been tagged yet — track the branch until the first tag exists.
    .package(url: "https://github.com/Amthal-Group/amthal-portal-sdk.git", branch: "main")
    // local checkout instead:
    // .package(path: "../portal-sdk/ios")
],
targets: [
    .target(name: "MyApp", dependencies: [.product(name: "AmthalPortal", package: "amthal-portal-sdk")])
]

from: "1.0.0" will not resolve today. SwiftPM version requirements match against Git tags, and this repository has no release tag yet. Use branch: "main" until the first tag is cut, then switch to a version requirement. With the local-path form (ios/, which carries an equivalent manifest so the SDK also opens standalone in Xcode) the package name is AmthalPortal, not portal-sdk.

Both manifests target swift-tools-version: 5.9 and .iOS(.v15).

4 — Set baseUrl (read this one twice)

This is the single most common integration mistake, and it does not look like a configuration error when it happens. baseUrl must be the full base URL of the portal deployment, including its deploy path prefix. The Amthal Client Portal ships with <base href="/portal/">, so on a typical deployment the correct value ends in /portal.

ValueVerdict
https://portal.example.com/portal✅ correct
https://portal.example.com/portal/✅ a trailing slash is tolerated and stripped
https://portal.example.com❌ drops the prefix — see below
https://portal.example.com/portal?x=1❌ never a query string; the Android constructor throws outright
http://portal.example.com/portal❌ HTTPS is mandatory outside loopback (step 10)

Why dropping the prefix breaks everything, quietly

Every host computes the navigation subtree it will allow as basePath + "/embed" — never a literal /embed. Give it https://portal.example.com and basePath is empty, so the SDK believes only /embed/* is in-bounds. The portal actually serves /portal/embed/*. The very first in-app navigation therefore looks off-subtree, the WebView cancels it, and the URL is handed to the system browser — your user is thrown out of your app into Safari or Chrome on a page they cannot log in to. Nothing in the error callbacks fires, because from the SDK's point of view it did its job.

Verify it — the check that catches most broken integrations

curl -sI https://portal.example.com/portal/embed/manifest.json | grep -i '^content-type'
# → content-type: application/json

And look at the body:

curl -s https://portal.example.com/portal/embed/manifest.json
# → {"portalVersion":"1.8.0","bridgeProtocolVersion":1,"minSdkVersion":"1.0.0"}

If the content type is text/html, you are being served the single-page app's index.html by a catch-all rewrite: either your path prefix is wrong, or the manifest asset is not deployed. The SDK will fail with manifestFailed and show a retry screen. The manifest is always fetched relative to the full base URL, never from the bare origin, so this one command tests both halves of your configuration at once.

Do not try to fix a path problem by pointing baseUrl at the bare origin and putting the prefix in the request instead. The prefix belongs in baseUrl; that is the value the confinement rule, the manifest URL and the initial load are all derived from.

5 — Find your branchId

An Amthal deployment is multi-tenant. The branch is the tenant/organisation whose forms, workflow and branding apply, and branchId is its numeric id passed as a string — "12", not 12.

In almost every app this is a build-time constant: put it in your environment config (EXPO_PUBLIC_BRANCH_ID, BuildConfig, an xcconfig). To look it up, either anonymous endpoint works: 

# resolves from the Host/Referer of the request
curl -s "https://api.example.com/Portal/Container/GetPortalConfig"

# resolves from an explicit origin
curl -s "https://api.example.com/Container/GetWebsiteContainerInfo?referer=https://portal.example.com"
# → { "succeeded": true, "data": { "branchID": 12, "companyName": "…", "primaryColor": "#…" } }

Do not derive branchId from a login response. A customer or contact login can legitimately carry a null branch, and an app that reads it from there works for every test account until it meets one that does not. Use your configured value.

If you omit branchId on an anonymous session the portal falls back to resolving the branch from the host name the WebView loaded. That is correct on a single-tenant host and ambiguous anywhere else — pass it whenever you know it.

6 — Obtain a token

Log in with your own call against the same backend the portal uses, and keep the token. The SDK only ever receives it over the bridge. 

curl -s -X POST "https://api.example.com/Portal/Authentication/Authenticate" \
  -H 'Content-Type: application/json' \
  -d '{"username":"customer@example.com","password":"…","rememberme":true}'
{
  "success": true,
  "authenticationResponse": {
    "token": "eyJhbGciOi…",       // ← this is auth.token
    "tokenExpiry": 1757000000,
    "branchID": "12",
    "employeeID": "4187"
  }
}

Where to keep it

The token, and only the token, in the platform keystore: iOS Keychain, Android Keystore, or expo-secure-store in Expo. Never AsyncStorage, never a plain file, never a log line. The SDK itself drops all portal log messages in release builds for the same reason.

Refreshing

When the portal's own refresh fails it emits authExpired and pauses. Mint a fresh token and hand it back — in React Native through the refresh function given to onAuthExpired (or the ref's updateAuth, which is the same code path); on the other hosts through updateAuth on the controller, view or sheet session. A full-screen "refreshing your session" overlay is up the whole time and clears when the portal acknowledges the new credentials. 

curl -s -X POST "https://api.example.com/Portal/Authentication/RefreshTokenWithExpiredToken" \
  -H 'Content-Type: application/json' \
  -d '{"token":"<the expired token>","contactID":4187}'
{
  "succeeded": true,
  "data": {
    "token": "…",
    "refreshtoken": "eyJhbGciOi…"   // ← the NEW token is HERE
  }
}

Read data.refreshtoken, not data.token. Both fields are populated and both look like tokens; the one you want is the second. This trips up essentially every first integration, and the symptom is a refresh that appears to succeed and then expires again immediately.

Anonymous sessions

For a public form in React Native, omit the auth prop entirely. The init message then carries no auth key at all, which is how the portal is told to render the public plane — and it also clears any credentials a previous launch left in the WebView's storage. 

<AmthalPortalForm config={config} request={request} /* no auth prop */ … />

Do not pass { token: '' } to mean the same thing in React Native. On the iOS, Android and Expo APIs the auth argument is not optional — there, an empty token string is how an anonymous session is declared, and the native side treats a blank token as no credential.

auth.user is optional everywhere: hand over the profile object your app already holds and the portal skips a profile round-trip. Omit it and the portal reconstructs the user from the token. Note the per-platform naming: TypeScript takes a user object, Swift takes userJSON and Kotlin takes userJson, both as already-serialised strings.

7 — Choose type and productID

type selects the application plane

typePlaneEffect
'internal' — the literal string Signed in Files the application against the signed-in contact; it appears in their requests list.
anything else — by convention 'external' Anonymous / public The server resolves a stand-in applicant; the submission belongs to nobody.

Getting type wrong fails silently. The portal tests type === "internal" and falls through for every other value. Open a signed-in user with 'external' and the form loads, validates and submits successfully — and the application then never appears in their history. There is no error to catch. Spell it internal, in lower case, for any authenticated submission.

productID is the form's id in the DMS catalogue

# anonymous / public catalogue
curl -s "https://api.example.com/Portal/PublicForms/GetCategories?formType=1"

# signed-in catalogue
curl -s "https://api.example.com/Portal/Forms/GetCategories?formType=1" \
  -H "Authorization: Bearer $TOKEN"
{
  "succeeded": true,
  "data": [
    {
      "id": 4,
      "name": "Maintenance",
      "subLevels": [
        { "productID": 830, "productName": "Maintenance Request", "active": true, "visibility": true }
      ]
    }
  ]
}

productID is what you pass to the SDK; productName is what you show the user. In most apps both already come from your own services or menu screen, which is driven by this same catalogue.

The three request shapes

RequestPortal route it resolves to
{ kind: 'newApplication', type, productID } {basePath}/embed/form/:type/:productID
{ kind: 'existingApplication', type, productID, batchID, headerID, readOnly } {basePath}/embed/form/:type/:productID/:batchID/:headerID/:readOnly
{ kind: 'path', path } Any other {basePath}/embed/… route — an escape hatch, not the normal way in.

On iOS and Android the same three shapes exist as PortalRequest.newApplication / .existingApplication / .path (Swift) and PortalRequest.NewApplication / .ExistingApplication / .Path (Kotlin). One difference worth knowing before you write the call: batchID and headerID are a number-or-string union in TypeScript but plain String on both native platforms.

8 — A minimal working screen

Each snippet below is the smallest thing that renders a form and reports the outcome. They are deliberately not feature-complete — locale switching, downloads, form delegation and custom loading UI are all on the API reference — but each one is a whole working screen you can paste in and run.

React Native Expo iOS Android

React Native — inline

import React, { useRef } from 'react';
import { Alert, StyleSheet, View } from 'react-native';
import {
  AmthalPortalForm,
  type AmthalPortalFormHandle,
  type PortalSdkConfig,
} from '@amthal-group/portal-react-native';

const config: PortalSdkConfig = {
  baseUrl: 'https://portal.example.com/portal',  // includes the deploy path prefix
  locale: 'en',
  theme: 'system',
  brandColor: '#121E4C',                         // colours the SDK's own splash and retry button
  minPortalVersion: '1.8.0',                     // optional floor: the oldest portal you tested
};

export function ServiceFormScreen({ token, productID, onClose }: {
  token: string;
  productID: number;
  onClose: () => void;
}) {
  const portal = useRef<AmthalPortalFormHandle>(null);

  return (
    <View style={styles.fill}>
      <AmthalPortalForm
        ref={portal}
        config={config}
        auth={{ token, branchId: '12' }}
        request={{ kind: 'newApplication', type: 'internal', productID }}

        onReady={() => console.log('portal ready')}
        onSubmitted={(result) => {
          // The SDK never auto-closes — decide for yourself what happens next.
          Alert.alert('Submitted', `Application ${result.applicationNo ?? ''}`);
          onClose();
        }}
        onCancelled={onClose}
        onError={(error) => console.warn(error.code, error.message)}
        onAuthExpired={async (refresh) => refresh({ token: await myRefreshToken(), branchId: '12' })}
        onCloseRequested={onClose}
      />
    </View>
  );
}

const styles = StyleSheet.create({ fill: { flex: 1 } });

declare function myRefreshToken(): Promise<string>;

onCloseRequested is optional in the type and effectively required in practice. The SDK installs its Android hardware-back handler only when you pass it. Omit it and back is not intercepted at all: instead of stepping back through the form, the platform default applies and your user leaves the screen mid-application. The three callbacks the compiler does enforce are onSubmitted, onCancelled and onError.

Expo — native iOS sheet

import { presentPortalSheet, type PortalSheetSession } from '@amthal-group/portal-expo';

const PORTAL_BASE_URL = 'https://portal.example.com/portal';
const BRANCH_ID = '12';

let sheet: PortalSheetSession | null = null;

export function openServiceForm(token: string, productID: number) {
  sheet = presentPortalSheet({
    config: { baseUrl: PORTAL_BASE_URL, locale: 'en', theme: 'system' },
    auth: { token, branchId: BRANCH_ID },
    request: { kind: 'newApplication', type: 'internal', productID },
    sheet: { detents: ['large', 'medium'], grabber: true, cornerRadius: 20 },

    onReady: ({ portalVersion }) => console.log('portal', portalVersion),
    onSubmitted: (result) => console.log('application', result.applicationNo),
    onCancelled: () => sheet?.dismiss(),
    onError: (error) => console.warn(error.code, error.message),
    onAuthExpired: async () => sheet?.updateAuth({ token: await myRefreshToken(), branchId: BRANCH_ID }),
    onClosed: () => { sheet = null; },
  });
}

declare function myRefreshToken(): Promise<string>;

sheet.dismiss() runs the SDK's unsaved-changes guard before closing, so it is safe to wire straight to a Cancel button. Every listener is torn down automatically when onClosed fires. Note that the Expo config object has no brandColor — the native sheet always uses the platform default tint for its interstitials.

iOS — UIKit, presented modally

import AmthalPortal
import UIKit

final class ServicesViewController: UIViewController, AmthalPortalDelegate {

    func openForm(token: String, productID: Int) {
        guard let baseURL = URL(string: "https://portal.example.com/portal") else { return }

        do {
            let config = try PortalConfig(
                baseURL: baseURL,               // includes the deploy path prefix
                locale: .en,
                theme: .system,
                brandColor: UIColor(red: 0.07, green: 0.12, blue: 0.30, alpha: 1),
                minPortalVersion: "1.8.0"
            )
            AmthalPortalViewController.present(
                from: self,
                config: config,
                request: .newApplication(type: "internal", productID: productID),
                auth: PortalAuth(token: token, branchId: "12"),
                delegate: self
            )
        } catch {
            // PortalConfigError.invalidBaseURL / .insecureBaseURL
            print("portal config rejected:", error)
        }
    }

    // MARK: AmthalPortalDelegate — every method has a default, override what you need.

    func portalReady(portalVersion: String) {
        print("portal", portalVersion)
    }

    func formSubmitted(_ result: FormSubmitResult) {
        // The SDK never auto-closes; dismiss when you are ready.
        dismiss(animated: true)
    }

    func portalError(_ error: PortalError) {
        print(error.code.rawValue, error.message)
    }
}

present(from:) wraps the controller in a UINavigationController presented as a page sheet, installs a Close button, and routes both that button and swipe-to-dismiss through the unsaved-changes guard. The initialiser throws — PortalConfigError.invalidBaseURL for a URL with no scheme or host, .insecureBaseURL for plain HTTP outside loopback — so a do/catch is not optional. There is also a SwiftUI wrapper, AmthalPortalView, that takes the same config plus closures.

Android — full-screen Activity

import android.content.Context
import android.util.Log
import com.amthalgroup.portal.*

fun openForm(context: Context, token: String, productID: Int) {
    val config = PortalConfig(
        baseUrl = "https://portal.example.com/portal",  // includes the deploy path prefix
        locale = PortalLocale.EN,
        theme = PortalTheme.SYSTEM,
        brandColor = 0xFF121E4C.toInt(),
        minPortalVersion = "1.8.0"
    )

    PortalFormActivity.start(
        context,
        config,
        PortalRequest.NewApplication(type = "internal", productID = productID),
        PortalAuth(token = token, branchId = "12"),
        object : AmthalPortalListener {

            override fun onPortalReady(portalVersion: String) {
                Log.i("Portal", "ready $portalVersion")
            }

            override fun onFormSubmitted(result: FormSubmitResult) {
                Log.i("Portal", "application ${result.applicationNo} / product ${result.productID}")
                // The SDK never auto-closes: finish the activity yourself when ready.
            }

            override fun onPortalError(error: PortalError) {
                Log.w("Portal", "${error.code} ${error.message}")
            }
        }
    )
}

PortalFormActivity is already declared in the SDK's own manifest, routes hardware back through the bridge, and wires file uploads for you — it is the fastest path on Android. PortalFormFragment and the bare AmthalPortalView exist for hosts that need the portal inside their own chrome. The PortalConfig constructor throws IllegalArgumentException for a bad baseUrl — including one carrying a query or fragment, which Android is the only platform to reject at construction time.

Of the listener's seven methods, exactly two have no default body and must be implemented: onFormSubmitted and onPortalError.

9 — Run it and verify

A successful first launch has a recognisable shape. You see the SDK's own loading splash for a moment — your brandColor, if you set one — and then the portal's form, edge to edge, with its action bar pinned to the bottom above the home indicator. Nothing bounces into a browser, and nothing sits on the splash for more than a few seconds.

Your checklist

  • The splash disappears. That means the portal sent ready; your onReady / onPortalReady callback fires at the same moment with the portal version.
  • You stay inside the app. Tapping through the form must never open Safari or Chrome. If it does, your baseUrl is missing the path prefix — go back to step 4.
  • The form is the right one, and on the right plane. Submit a test application and confirm it appears in that customer's request list in the portal. If it submits but never appears, type is not the literal 'internal' — step 7.
  • Back behaves. On Android, hardware back should step back through a multi-step form rather than leaving the screen. If it leaves immediately, you have not passed onCloseRequested.
  • Submission reaches you. onSubmitted fires with the application number, and the screen is still open — closing it is your code's job.

When it does not load, read the error code first

Every failure arrives as a typed code on your error callback. These four cover essentially every first-run problem:

CodeWhat it actually means on day one
manifestFailed The manifest was not JSON, could not be fetched, or timed out. Nine times out of ten the path prefix is wrong and you were served the SPA's HTML. Re-run the curl -sI from step 4.
versionIncompatible One of three gates failed: the portal's bridgeProtocolVersion is not 1, the portal is older than your minPortalVersion, or the SDK is older than the manifest's minSdkVersion. Compare your numbers against the manifest body you already fetched.
bridgeTimeout The page loaded but the portal never said hello within 15 seconds — usually a portal build without the embed shim, or a URL that landed on a non-embed route.
loadFailed A generic load failure — and, in release builds, what you get for an insecure baseUrl. Check the message text, which names the reason.

The full list of eight codes, what raises each one per platform, and which ones auto-retry when connectivity returns, is on Troubleshooting.

Smoke-testing without a device

Against a -dev build of the portal you can drive the embed routes from a desktop browser, with a mock host standing in for the native SDK. This is the fastest way to confirm a productID or check an Arabic layout before you rebuild an app: 

{baseUrl}/embed/form/external/{productID}?mockEmbed=1

# authenticated, and with locale / theme / font scale overrides
{baseUrl}/embed/form/internal/{productID}?mockEmbed=1&mockToken=<jwt>&mockBranch=12&mockLocale=ar&mockTheme=dark&mockFontScale=1.2

The harness is installed only on a -dev portal build, and the default is anonymous — add mockToken and mockBranch to exercise the authenticated plane. mockPlatform=ios|android|react-native changes which transport hint the portal sees.

10 — Developing against a plain-HTTP portal

HTTPS is mandatory. Plain http:// is accepted only for loopback hosts — localhost and 127.0.0.1 everywhere, plus 10.0.2.2 (the Android emulator's alias for your machine) on the React Native and Android hosts, and ::1 on iOS and Android.

An Amthal portal dev server is often bound to a tenant hostname instead, because the backend resolves the tenant from the request host. For that case there is a development-only escape hatch, and it takes two things — the flag alone is not enough:

  1. allowInsecureHttp on the config (note the casing on Swift, where it is allowInsecureHTTP). It is build-gated at the source: honoured only under __DEV__ in React Native, #if DEBUG on iOS and Expo, and a debuggable application on Android. A release build enforces HTTPS no matter what you pass.
  2. A platform transport exception — an ATS NSExceptionDomains entry in Info.plist (or ios.infoPlist in app.config.ts, followed by a prebuild) on iOS, or a scoped network_security_config in your debug source set on Android.

Both are inert in a release build, but both are also a review finding waiting to happen. Keep them in debug-only configuration rather than switching them on globally. If your forms take photo or file attachments you will also need the usual iOS camera and photo-library usage strings; on Android, file uploads work out of the box under PortalFormActivity.

11 — Before you ship

  • Strip the development hatches from release configuration — allowInsecureHttp, the ATS exception, the network security config.
  • Scope enableLogging to development. The SDK drops portal log messages in release builds regardless, but leaving the flag on states an intent you do not have.
  • Set minPortalVersion to the oldest portal build you have actually tested against, and present versionIncompatible to the user as "please update the app" rather than a generic failure.
  • Confirm the token never leaves the keystore — not into analytics, not into a crash report's breadcrumbs, not into a URL. Credentials travel only over the bridge.
  • Decide what happens after a submission. The SDK will sit on the submitted form forever if you let it; onSubmitted is where your app navigates, refreshes a list, or shows its own confirmation.
