API reference

Every public type, property, method and callback of the Amthal Portal SDK, for all four hosts: the React Native wrapper, the Expo native sheet, the iOS Swift package and the Android library. All four speak Amthal Bridge Protocol v1 and all four report SDK version 1.0.0.

The four hosts deliberately share one vocabulary — baseUrl, locale, theme, fontScale, a request, an auth object and an error code — so that a behaviour you learn on one platform transfers to the next. Where they differ, they differ for a concrete reason, and every such difference is called out in Cross-platform differences. Read that section before you assume a field exists everywhere; three of the traps below are pure casing.

1. Shared shapes — request, auth, result, error 2. React Native — @amthal-group/portal-react-native 3. Expo — @amthal-group/portal-expo 4. iOS — AmthalPortal (Swift) 5. Android — com.amthalgroup:portal-sdk (Kotlin) 6. Cross-platform differences

baseUrl must include the portal's deploy path prefix. The Client Portal ships with <base href="/portal/">, so the correct value is https://portal.example.com/portal, never https://portal.example.com. Every host computes its navigation boundary as basePath + "/embed", so dropping the prefix makes the portal's very first in-app navigation look off-subtree and throws the user out into the system browser. This is the single most common integration failure.

1. Shared shapes

These four shapes — what to show, who is asking, what came back, what went wrong — are the whole data surface of the SDK. The TypeScript definitions are canonical (@amthal-group/portal-bridge); Swift and Kotlin mirror them type-for-type with the naming differences noted.

Request — what the portal should show

A request is mapped to a portal route and the WebView is navigated straight to it: the URL is the request. Credentials never appear in it — they travel over the bridge only. 

// TypeScript — React Native and Expo
type PortalFormRequest =
  | { kind: 'newApplication';      type: string; productID: number }
  | { kind: 'existingApplication'; type: string; productID: number;
      batchID: number | string; headerID: number | string; readOnly: boolean }
  | { kind: 'path'; path: string };
// Swift
public enum PortalRequest: Equatable, Sendable {
    case newApplication(type: String, productID: Int)
    case existingApplication(type: String, productID: Int,
                             batchID: String, headerID: String, readOnly: Bool)
    case path(String)
    public var path: String { /* mirrors requestToPath() */ }
}
// Kotlin
sealed class PortalRequest {
    data class NewApplication(val type: String, val productID: Int) : PortalRequest()
    data class ExistingApplication(
        val type: String, val productID: Int,
        val batchID: String, val headerID: String, val readOnly: Boolean
    ) : PortalRequest()
    data class Path(val path: String) : PortalRequest()
    fun toPath(): String
}
Route each request resolves to (requestToPath)
KindResolved path
newApplication /embed/form/{type}/{productID} — type is URI-component encoded
existingApplication /embed/form/{type}/{productID}/{batchID}/{headerID}/{readOnly}
path A leading / is added if missing, and /embed is prefixed when the path does not already start with it

type must be the literal string 'internal' for a signed-in submission. The portal compares it against that exact value (isInternalForm = type() === "internal"). Open a signed-in user with 'external' and the submission still succeeds — but the application never appears in that user's history. It fails silently, which is why it is worth a line of code to get right.

Auth — the credentials handed over the bridge

The same three values, four spellings
HostTypeFields
React Native PortalAuthState token: string · branchId?: string | null · user?: unknown
Expo (JS) PortalAuthState Same three. user is JSON-stringified into userJSON before it crosses to native
iOS PortalAuth token: String · branchId: String? · userJSON: String?
Android PortalAuth token: String · branchId: String? = null · userJson: String? = null — toString() redacts all three

user / userJSON / userJson is optional everywhere: omit it and the portal rebuilds the user object from its own profile endpoint using the token. Supply it only when you already hold that object and want to save the round trip.

Anonymous sessions are a React Native feature. Omit the auth prop entirely and init carries no auth key at all — that is how the portal is told to render the public plane and to drop credentials a previous launch left in WebView storage. Do not pass { token: '' } to mean the same thing. The Expo, iOS and Android APIs take a non-optional auth object, so a blank token is the only shape available there.

Submit result

interface FormSubmittedPayload {   // exported as FormSubmitResult by both wrappers
  productID: number;
  applicationNo?: number | string;
  batchID?: number | string;
  headerID?: number | string;
  raw?: unknown;                  // anything else the portal surfaces; opaque to the SDK
}

The SDK never auto-closes on submit on any platform. Your callback decides what happens next — close the screen, show a receipt, navigate to a status page. On the Expo native sheet, raw is dropped when the result is serialized across to JavaScript even though the TypeScript type includes it; read the typed fields there.

Error

Eight codes, identical on every platform: offline, loadFailed, httpError, manifestFailed, bridgeTimeout, versionIncompatible, authExpired, webProcessTerminated. What triggers each one, and which are auto-retried, is on the Troubleshooting page.

Error object per host
HostShape
React Native / ExpoPortalErrorInfo { code: PortalErrorCode; message?: string; httpStatus?: number }
iOSPortalError { code: PortalErrorCode; message: String } — .httpError(Int) carries the status as an associated value, plus code.httpStatus: Int? and code.rawValue: String
AndroidPortalError(code: PortalErrorCode, message: String? = null, httpStatus: Int? = null); each enum member exposes .wire

Locale and theme

Both are closed sets on every platform. Locale is 'en' | 'ar' — there is no third value, and 'ar' also flips the portal's document direction to RTL. Theme is 'light' | 'dark' | 'system' and defaults to system; it drives the portal's own UI and the SDK's loading and error overlays, so setting it wrong produces a visible flash of the wrong scheme before the portal renders. In Swift they are PortalLocale / PortalTheme (.en, .ar; .light, .dark, .system); in Kotlin the same enums expose the wire string as .wire.

2. React Native — @amthal-group/portal-react-native

A pure-TypeScript wrapper over react-native-webview that renders the portal inline, inside your own navigation. It is the only host that supports form delegation and the only one that lets you replace the loading and error UI with your own components. Peer dependencies: react >= 18, react-native >= 0.72, react-native-webview >= 13. 

import { AmthalPortalForm, type AmthalPortalFormHandle } from '@amthal-group/portal-react-native';

const portal = useRef<AmthalPortalFormHandle>(null);

<AmthalPortalForm
  ref={portal}
  config={{ baseUrl: 'https://portal.example.com/portal', locale: 'en', theme: 'system',
            brandColor: '#121E4C' }}
  auth={{ token, branchId: '12' }}
  request={{ kind: 'newApplication', type: 'internal', productID: 42 }}
  onSubmitted={(r) => navigation.replace('Receipt', { applicationNo: r.applicationNo })}
  onCancelled={() => navigation.goBack()}
  onError={(e) => console.warn(e.code, e.message)}
  onCloseRequested={() => navigation.goBack()}
  style={{ flex: 1 }}
/>

3. Expo — @amthal-group/portal-expo

Presents the native iOS SDK inside a UISheetPresentationController, driven from JavaScript. The chrome, the hardening and the interstitials are all native, which is why the module is Apple-only ("platforms": ["apple"]) and why it needs a development build — Expo Go cannot load it. The pod targets iOS 15.1. 

import { presentPortalSheet } from '@amthal-group/portal-expo';

const session = presentPortalSheet({
  config: { baseUrl: 'https://portal.example.com/portal', locale: 'en', theme: 'system' },
  auth: { token, branchId: '12' },
  request: { kind: 'newApplication', type: 'internal', productID: 42 },
  sheet: { detents: ['large', 'medium'], grabber: true },
  onSubmitted: (r) => console.log('submitted', r.applicationNo),
  onError: (e) => console.warn(e.code, e.message),
  onClosed: () => console.log('sheet closed'),
});

// later
session.updateAuth({ token: fresh });
session.dismiss();

PortalSdkConfig

The same field names as React Native minus brandColor: baseUrl (required), locale, theme, fontScale, minPortalVersion, allowedOrigins, enableLogging, allowInsecureHttp. The native side applies defaults while parsing: locale → en, theme → system, fontScale → 1.0, enableLogging → false, and allowInsecureHttp is forced to false outside DEBUG builds.

There is no brandColor on the Expo sheet. It is neither declared in the TypeScript config nor read by the native module, so the sheet always uses the platform default tint for its loading interstitial. If brand-coloured waiting matters to you, use the inline React Native component or the native iOS SDK directly.

Presentation rejections

present can reject before any session exists. Each rejection is surfaced through onError as loadFailed with the native code in the message: E_ALREADY_PRESENTED (a sheet is already up), E_NO_PRESENTER (no view controller to present from), E_CONFIG (the config was rejected — almost always the base URL), E_ARGS (a malformed request or auth object) and E_MODULE (the native module is missing, i.e. you are running Expo Go or an un-prebuilt app).

The underlying native module is named AmthalPortalNative and emits onReady, onSubmitted, onCancelled, onError, onAuthExpired, onNavigate and onClosed, with methods present, updateAuth, configure and dismiss. You normally use presentPortalSheet rather than the module directly.

4. iOS — AmthalPortal (Swift)

A Swift package (tools version 5.9, minimum iOS 15) whose product and library are both named AmthalPortal. The root Package.swift is what SwiftPM resolves when you add the repository by Git URL; ios/Package.swift exists for local-path consumption from a checkout. No release tag exists yet — depend on branch: "main" until the first tag is cut.

PortalConfig

public init(
    baseURL: URL,
    locale: PortalLocale = .en,
    theme: PortalTheme = .system,
    fontScale: Double = 1.0,
    brandColor: UIColor? = nil,
    minPortalVersion: String? = nil,
    allowedOrigins: Set<String>? = nil,      // nil ⇒ [baseURL.host]
    enableLogging: Bool = false,
    allowInsecureHTTP: Bool = false
) throws

Note the casing: allowInsecureHTTP here, against allowInsecureHttp everywhere else. The initializer throws PortalConfigError.invalidBaseURL(URL) when the URL has no scheme or host, and .insecureBaseURL(URL) for plain HTTP to a non-localhost host. Both conform to Error, Equatable and LocalizedError, so you can present them directly. Localhost means localhost, 127.0.0.1, ::1, [::1] or any *.localhost.

baseURL, basePath (the path minus trailing slashes, "" at the root) and allowInsecureHTTP are immutable lets — and the stored insecure flag is already build-gated, so a release build cannot be pointed at an HTTP portal by one boolean. locale, theme, fontScale, brandColor, minPortalVersion, allowedOrigins and enableLogging are var.

What brandColor actually colours on iOS: the loading spinner, and only the loading spinner. The retry button is a stock filled UIButton and keeps the system tint. (The source's own doc comment claims the retry affordance too — it overstates it.)

AmthalPortalDelegate

A @MainActor class protocol in which every method has a default no-op, so you implement only what you need. In practice that means formSubmitted, portalError and closeRequested are the ones worth writing.

5. Android — com.amthalgroup:portal-sdk:1.0.0

A Kotlin library: minSdk 24, compileSdk 35, Java/JVM 17. The Gradle wrapper is committed and pinned (8.9, with a distribution checksum), so a clean clone builds with ./gradlew :portal-sdk:assembleRelease from the android/ directory; the AAR lands under android/portal-sdk/build/outputs/aar/.

Three entry points, in increasing order of control: PortalFormActivity (start it and forget it), PortalFormFragment (inside your own navigation graph) and AmthalPortalView (a plain FrameLayout you place anywhere).

PortalConfig

data class PortalConfig(
    val baseUrl: String,
    val locale: PortalLocale = PortalLocale.EN,
    val theme: PortalTheme = PortalTheme.SYSTEM,
    val fontScale: Float = 1f,
    @ColorInt val brandColor: Int? = null,
    val minPortalVersion: String? = null,
    val allowedOrigins: Set<String> = emptySet(),
    val certificatePinner: ((X509Certificate) -> Boolean)? = null,
    val enableLogging: Boolean = false,
    val allowInsecureHttp: Boolean = false
)

The constructor throws IllegalArgumentException. It rejects fontScale <= 0, a baseUrl with no scheme or no host, a non-HTTPS URL whose host is not a loopback address (localhost, 127.0.0.1, 10.0.2.2, ::1) unless allowInsecureHttp is set, and — uniquely among the four platforms — a baseUrl carrying a query string or a fragment. Build your config where you can catch that, not inside onCreate's happy path.

Computed members you can rely on: origin (scheme, host and non-default port, no path), basePath ("" at the root, /portal for a prefixed deploy), normalizedBaseUrl (trailing slashes stripped — the string all portal URLs are concatenated onto) and allowedHosts. Methods: isUrlOriginAllowed(url: String?): Boolean, isInsecureHttpHonoured(context): Boolean (true only in a debuggable app) and isBaseUrlTransportAllowed(context): Boolean.

certificatePinner is Android-only and covers SDK-initiated HTTPS only — the manifest fetch and downloads. The portal page load itself goes through the system WebView network stack, which exposes no pinning hook, so pin at the network edge if you need full coverage. brandColor tints the loading progress indicator.

PortalFormActivity and PortalFormFragment

PortalFormActivity.start(context, config, request, auth, listener)   // @JvmStatic
fun updateAuth(auth: PortalAuth)

PortalFormFragment.newInstance(config, request, auth, listener)     // @JvmStatic
fun updateAuth(auth: PortalAuth)
fun updateConfigure(locale: PortalLocale? = null, theme: PortalTheme? = null, fontScale: Float? = null)

Both use the same handoff: a listener is not parcelable, so the whole session is stashed in an in-memory store and only a lookup key travels in the Intent or arguments. That survives configuration changes but not process death — after process death the host finds no session and finishes or removes itself immediately, which is the behaviour to expect when you test with "Don't keep activities" enabled. PortalFormActivity adds FLAG_ACTIVITY_NEW_TASK when started from a non-Activity context, routes hardware back through the bridge, and finishes itself on onCloseRequested — but never on submit or cancel. File-chooser wiring is automatic in both.

AmthalPortalListener

fun onPortalReady(portalVersion: String) {}
fun onFormSubmitted(result: FormSubmitResult)                 // no default — you must implement it
fun onFormCancelled() {}
fun onPortalError(error: PortalError)                         // no default — you must implement it
fun onOpenExternal(url: String): Boolean = false              // true ⇒ you consumed the URL
fun onNavigate(path: String, title: String?) {}
fun onCloseRequested() {}

Everything is delivered on the main thread. onFormSubmitted and onPortalError are the two members with no default body, so the compiler makes you handle both a successful submission and a failure — which is the right pair to be forced into. For PortalErrorCode.AUTH_EXPIRED, fetch a fresh token and call updateAuth; the SDK shows an interstitial meanwhile and auto-retries retriable errors when connectivity returns. Leaving onOpenExternal at its default fires an ACTION_VIEW intent, which opens Custom Tabs when the default browser supports them.

Android hardware back on React Native. Omitting onCloseRequested does not merely skip a callback — the SDK installs no back handler at all, and the platform default applies, so back can pop your navigator out from under a half-filled form. Supply it on every screen that embeds the portal.

Two behaviours are identical everywhere and worth stating once more, because integrations routinely assume the opposite: the SDK never auto-closes on submit, and credentials never travel in a URL — only in init and auth bridge payloads. If you find yourself putting a token in a path or query, stop: the bridge already carries it.
