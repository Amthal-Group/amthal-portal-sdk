Amthal Portal Embed SDK

Put the Client Portal inside your own app

The Amthal Portal SDK embeds the Client Portal — and every form your tenant has published in it — as a native screen in your iOS, Android, React Native or Expo app: your app owns the chrome, the session and the navigation, while the portal keeps rendering, validating and submitting the forms.

What your users actually see

These are real captures from a shipping app. Nothing in them is a browser: no address bar, no page chrome, no zoom. The form draws edge to edge, the action bar is pinned to the safe area, and the loading state is your brand colour from the very first frame — before the web view has had a chance to say anything.

Why it is built this way

Forms in the Optimum platform are configuration, not code: a tenant adds a field, reorders a step or publishes a whole new application type, and it must be live for customers the same day. Shipping that through an app-store release cycle is not workable. So the SDK splits the problem in three, and each piece does only what it is best at.

  • A native shell

    Your app owns presentation, the session and the back stack. The SDK gives you a view (React Native, Android), a view controller (iOS) or a modal sheet (Expo) — plus the things a web view cannot do for itself: loading and error interstitials, hardware-back handling, an unsaved-changes guard, authenticated downloads and file uploads.

  • A web form engine

    The Client Portal renders the form from the tenant's DMS catalogue and submits it to the Optimum Core API. Add a field in the back office and it appears in your app on the next open, with no release. The portal is themed server-side from the branch, so the form already looks like the tenant it belongs to.

  • One bridge

    Between them sits Amthal Bridge Protocol v1 — a small, versioned, JSON message contract. Every host implements exactly the same messages, so behaviour is identical across the four runtimes except where the capability matrix below says otherwise. Credentials travel over that bridge, never in a URL.

The consequences worth knowing up front

  • The SDK never closes itself on submit. When a submission succeeds you get onSubmitted / formSubmitted with the product id and the application number; what happens next — a confirmation screen, a pop, a second form — is your decision.
  • Navigation is confined. Main-frame navigation is allowed only inside basePath + /embed. Anything outside that subtree is handed to your openExternal hook, or opened outside the web view.
  • The version handshake is strict. Before the form is shown, the SDK fetches /embed/manifest.json and refuses to continue if the portal speaks a different bridge protocol version, is older than your minPortalVersion, or is newer than the SDK build it is talking to.

Honest differences

Everything not listed here behaves identically on all four hosts: the version handshake and error interstitials, auth handoff and authExpired recovery, navigation confinement, runtime configure of locale, theme and font scale, and file uploads from the form.

Form delegation is React-Native-only today

If your app must own the network calls the form makes — because you proxy them, sign them, or run them through your own offline queue — use the inline <AmthalPortalForm/> and its onFormOp prop. The native iOS and Android hosts do not implement formOp; the Expo sheet rejects the option immediately rather than silently ignoring it.

Sixty-second quickstart

This is the React Native path, the most used one. It assumes you already have the two values only Amthal can give you: a portal base URL and a productID. If you do not, Getting Started walks through obtaining every one of them.

Terminal 
npm install @amthal-group/portal-react-native react-native-webview
cd ios && pod install
ServiceRequestScreen.tsx 
import { AmthalPortalForm } from '@amthal-group/portal-react-native';

<AmthalPortalForm
  style={{ flex: 1 }}
  config={{ baseUrl: 'https://portal.example.com/portal', locale: 'en', theme: 'system' }}
  // Omit `auth` entirely for the anonymous plane. Never pass { token: '' }.
  auth={{ token, branchId: '12' }}
  request={{ kind: 'newApplication', type: 'internal', productID: 41 }}
  onSubmitted={(result) => showReceipt(result.applicationNo)}
  onCancelled={close}
  // Required, or the Android hardware-back handler is never installed.
  onCloseRequested={close}
  onError={(error) => reportProblem(error.code, error.message)}
/>

Three callbacks are required by the type (onSubmitted, onCancelled, onError) and a fourth, onCloseRequested, is required in practice: without it the wrapper installs no Android back handler at all, and the hardware back button closes your screen mid-form. Everything else — refresh-on-expiry, downloads, external links, a custom splash — is opt-in and covered in the API Reference.

The base URL must include the portal's deploy path prefix

The Client Portal ships with <base href="/portal/">, so the correct value is https://portal.example.com/portal — not https://portal.example.com. Navigation confinement is computed as basePath + /embed, so dropping the prefix makes the portal's very first navigation look like it left the subtree, and the user is thrown into the system browser. It is the single most common integration mistake. Confirm it with one command: curl -s {baseUrl}/embed/manifest.json must return JSON, not HTML.

Two values that fail silently when they are wrong

type must be the literal string 'internal' for a signed-in submission. A signed-in user opened with any other value submits successfully down the public plane, and the application never appears in their history — no error anywhere.

For an anonymous session, omit auth entirely. Passing { token: '' } is not the same thing: an absent auth key is how the portal is told it is on the public plane and made to drop stored credentials.

What happens when a form opens

Worth reading once: almost every support question is really a question about which of these five steps did not complete.

  1. The SDK fetches the manifest

    GET {baseUrl}/embed/manifest.json — always relative to the full base URL, never to the bare origin. It carries portalVersion, bridgeProtocolVersion and an optional minSdkVersion. Failure here is manifestFailed; a version mismatch is versionIncompatible.

  2. The web view loads the embed route

    Your request is turned into a path under /embed — for a new application, /embed/form/{type}/{productID}. The SDK's loading interstitial is on screen throughout.

  3. The portal says hello, the host replies init

    init is where the credentials, locale, theme and font scale cross — over the bridge, never in the URL. If no hello arrives within 15 seconds of the page loading, you get bridgeTimeout.

  4. The portal says ready

    Angular has booted, the credentials have been applied and the first embed route has resolved. This is the moment the SDK hides its skeleton and your onReady fires — exactly once per page load.

  5. The user submits — and you decide what happens next

    formSubmitted carries productID and, where the portal returns one, applicationNo, batchID and headerID. The SDK does not dismiss itself. If the session expired mid-form instead, you get authExpired, the form pauses, and it resumes the moment you hand back a fresh token.

The messages, payload shapes and the normative timings are documented in full on the Bridge Protocol page; every error code and what actually triggers it is on Troubleshooting.
